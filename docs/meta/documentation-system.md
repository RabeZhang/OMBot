# Documentation System

**验证状态**

- 文档体系状态：已替换旧的散列方案文档
- 结构状态：已按 `product / architecture / modules / meta / examples` 分层
- 执行状态：后续文档更新必须遵循本文件约束

**核心理念**

- 文档系统要和代码结构、产品边界、运行时事实一致。
- 文档维护的目标不是“记录想法”，而是“维持可用、可信、可判断的系统知识”。
- 单篇文档不要同时承担需求草案、实现细节、历史讨论三种角色。

**当前实现方式**

当前 `docs/` 采用以下结构：

```text
docs/
  Agent.md
  architecture/
  meta/
  modules/
  product/
  examples/
```

目录职责：

- `Agent.md`
  - 文档系统总入口
  - 模块索引
  - 阅读顺序
- `product/`
  - 项目定位、当前状态、主要缺口
- `architecture/`
  - 跨模块的边界原则
- `modules/`
  - 对应 `src/` 里的真实模块
- `meta/`
  - 文档维护规则、评分标准、维护 Agent 说明
- `examples/`
  - 示例输入、示例配置、示例事件文件

单篇文档格式要求：

1. `验证状态`
   - 记录当前落地程度
   - 记录是否仍为目标能力
   - 记录文档与代码是否已校对
2. `核心理念`
   - 解释该模块存在的目的
   - 解释边界和非目标
3. `当前实现方式`
   - 记录现在代码如何实现
   - 明确主要源码路径
   - 说明已实现、部分实现、未实现的边界

清理规则：

- 需求讨论稿、阶段性 checklist、已经被新体系吸收的设计稿，应从主文档区删除。
- 如果某个旧方案已经废弃，不应继续在当前主文档中以“现行方案”出现。
- 同一主题只保留一个主文档入口，避免多个文件同时声明不同事实。
